# Prototype A: Claude Tool Runner + Deepgram STT + TTS

## Purpose
Measure latency and German-language accuracy for a voice-controlled circuit-tracks
agent built on the Claude API Tool Runner, with STT and TTS as separate pipeline
stages. This is one of two comparable prototypes (see
[voice-agent-realtime-api.md](voice-agent-realtime-api.md)) built to decide the
production architecture for the accessibility voice agent.

## Background
Target users have limited/no arm mobility and control the agent via a single
switch-accessible button. See project memory `project_voice_to_notes` for prior
related work (record_melody/transcribe tools) and the session discussion that
preceded this spec for full context on the staged-vs-persist and barge-in
requirements — this prototype deliberately narrows scope to a single measurable
round trip and does not implement those yet.

## Scope (deliberately minimal)
- **One round trip only**: button press → record → transcribe → one Claude tool
  call → spoken confirmation. No multi-turn context, no staged/preview state, no
  persist-on-command step, no barge-in interrupt.
- **Trigger**: keyboard key (e.g. spacebar) press-and-hold stands in for the
  physical AT switch. Press to start recording, release to stop.
- **Tool set** (fixed, same across both prototypes, for a fair comparison):
  - `set_bpm`
  - `set_pattern`
  - `set_synth_params`
  - `play_notes`
- **Language**: German only for this test.
- **Test phrases** (same two used for both prototypes):
  1. Vague/open-ended, e.g. "Mach den Beat schneller" (make the beat faster —
     requires the model to infer a concrete `set_bpm` delta or value).
  2. Precise, e.g. "Setz das Tempo auf 120 BPM" (set tempo to 120 BPM — direct
     mapping to `set_bpm`).

## Out of scope
- Real AT switch/HID hardware integration.
- Staged/preview song state and explicit persist step.
- Full circuit-tracks tool surface.
- Multi-turn conversation memory.
- Production error handling / retry logic beyond what's needed to get a clean
  latency measurement.

## Architecture

```
[hold spacebar] → mic capture (local)
        ↓ (on release)
   Deepgram streaming STT (German)
        ↓ final transcript
   Claude API Tool Runner turn
     - system prompt: narrow, circuit-tracks domain only
     - tools: set_bpm, set_pattern, set_synth_params, play_notes
     - prompt caching on system prompt + tool defs
        ↓ tool call executed against circuit-tracks MCP server (staging TBD later)
        ↓ short confirmation text generated by Claude
   TTS (vendor TBD — ElevenLabs or Azure Neural, pick one for this test)
        ↓
   audio playback
```

## Prerequisites (must be set up before implementation starts)
- [ ] Anthropic API key with access to `claude-sonnet-5` (and optionally
      `claude-opus-5` with Fast Mode beta, for an effort/speed comparison).
- [ ] Deepgram API key with Nova-3 streaming access, German language enabled.
- [ ] TTS vendor account (ElevenLabs or Azure Speech — pick one; note which was
      used in the results writeup since it affects the numbers).
- [ ] Local mic input working in the prototype's runtime environment.
- [ ] circuit-tracks MCP server running and reachable (existing `connect` tool).

## What to build
1. A standalone script (not inside Claude Code) using:
   - `client.beta.messages.tool_runner` with `@beta_tool`-decorated functions
     wrapping the 4 fixed circuit-tracks tools.
   - Deepgram streaming SDK for STT.
   - Chosen TTS SDK for playback.
2. Instrumentation: timestamp at (a) key release, (b) STT final transcript
   received, (c) Claude tool-call response received, (d) first TTS audio byte
   played. Log all four per trial.
3. A small harness to run both test phrases N times each (suggest N=10) and
   compute median/p95 latency per stage and end-to-end.

## Success criteria
Both latency and accuracy are tracked as co-equal criteria — this prototype is
not "successful" or "failed" on its own, it produces numbers to compare against
Prototype B.

- **Latency**: end-to-end time from key-release to first audio played back,
  broken down by stage (STT / LLM+tool-call / TTS), median and p95 across trials.
- **Accuracy**:
  - Did the transcript correctly capture the German phrase? (STT accuracy)
  - Did Claude call the correct tool with correct/reasonable parameters for
    both the vague and precise phrasing? (intent-to-tool-call accuracy)
  - Was the spoken confirmation correct and understandable?

## Open questions to resolve during implementation
- Does prompt caching meaningfully reduce latency at this small a tool/prompt
  size, or is the win only visible with the full tool surface?
- How much does Claude effort level (`low`/`medium`) change latency vs. answer
  quality for the vague phrase?
- Is a single TTS vendor call fast enough, or does streaming TTS (start
  playback before full text is generated) matter even at this short
  confirmation length?
